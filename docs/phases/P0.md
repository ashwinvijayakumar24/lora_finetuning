# P0 — Hand-written LoRA, verified against PEFT

**Status:** done. All oracle tests are green: 53 default tests and 1 slow test pass.

P0 builds the LoRA layer that every later phase trains, saves, and serves. It is
written by hand so the mechanics are understood, not just used. Hugging Face PEFT
is the *oracle*: the reference implementation that the tests compare against. No
PEFT code runs inside `playparse.lora`.

## What was built

| File | What it does |
|---|---|

| `playparse/lora/config.py` | `LoRAConfig` (r, alpha, dropout, target_modules) and PEFT config conversion |
| `playparse/lora/inject.py` | `inject_lora`, `merge_lora`, `unload_lora`, `lora_state_dict`, parameter counts |
| `playparse/lora/io.py` | Save and load adapters in PEFT's on-disk format |
| `playparse/lora/memory.py` | Analytic parameter counts and training-memory estimates |
| `scripts/p0_param_table.py` | Writes `results/p0/param_table.{json,md}`, with an optional MPS measurement |

### Public API (what P2, P3, P5 will call)

```python
from playparse.lora import (
    LoRAConfig, LoRALinear,
    inject_lora, merge_lora, unload_lora,
    lora_state_dict, load_lora_state_dict, trainable_parameters,
    count_trainable, count_total,
    save_adapter, load_adapter, read_adapter,
)

cfg = LoRAConfig(r=16, alpha=32, dropout=0.05, target_modules="all-linear")
model = inject_lora(model, cfg, adapter_dtype=torch.float32)  # in place; freezes the rest
opt = torch.optim.AdamW(trainable_parameters(model), lr=2e-4)
save_adapter(model, cfg, "runs/r5/adapter", base_model_name_or_path="meta-llama/Llama-3.2-1B-Instruct")
model, cfg = load_adapter(base_model, "runs/r5/adapter")       # also loads PEFT-trained adapters
plain = merge_lora(model)                                      # nn.Linear everywhere, weights merged
```

## How LoRA works, through this code

### The idea

Fine-tuning changes a weight matrix `W` (shape `out × in`) into `W + ΔW`. Full
fine-tuning learns every entry of `ΔW`. LoRA bets that the useful change has low
rank, which means it can be written as the product of two thin matrices:

```
ΔW = (α / r) · B · A        A: r × in      B: out × r      r ≪ in, out
y  = x·Wᵀ + (α / r) · (x·Aᵀ)·Bᵀ
```

**A concrete example.** For `q_proj` in Llama 3.2 1B, `W` is 2048 × 2048, which is
4.2M numbers. With r=16, A is 16 × 2048 and B is 2048 × 16, which is 65,536
numbers in total, or 1.6% of the full matrix. `W` stays frozen, and only A and B
are trained.

`LoRALinear.forward` computes exactly this. The base layer runs unchanged, and
the low-rank path is added on top:

```python
result = self.base_layer(x)
result = result + self.lora_B(self.lora_A(self.dropout(x))) * self.scaling
```

The low-rank path never forms the full `out × in` matrix `B·A`. It multiplies `x`
by A (down to r dimensions) and then by B (back up). That keeps the extra compute
small.

### Why B starts at zero

A is initialised randomly (Kaiming-uniform, the same init `nn.Linear` uses), and B
is all zeros. Then `B·A = 0`, so **at step 0 the adapted model computes exactly
the same function as the base model**. Training starts from the pretrained
behaviour instead of from a randomly perturbed copy of it. The test
`test_zero_init_output_equals_base_exactly` checks this with `torch.equal`: the
outputs are bit-identical, not merely close.

Why not make both zero? Then nothing could learn. The gradient of B is
proportional to A, and the gradient of A is proportional to B. If both are zero,
both gradients are zero forever. With A random and B zero, B gets a gradient on
the first step, and A starts learning one step later. A related trap appears in
testing: with B = 0, A's gradient is exactly zero, so a gradient-comparison test
passes even if A's gradient is wrong. That is why the oracle tests set B to random
values first (`randomize_lora`).

### Why scale by α / r

The update is multiplied by `scaling = alpha / r`. Without it, the size of the
update would grow with r, because `B·A` is a sum of r rank-one terms. Changing r
would then also change the effective learning rate, and you would have to retune
the learning rate for every rank. Dividing by r roughly cancels that growth. The
usual setting `α = 2r` gives a scaling of 2 at every rank.

PRD §8.4's sweep includes "fixed α = 16 across ranks" for this reason. At r=64 that
gives a scaling of 0.25, which shrinks the update, and the sweep will show whether
that leads to underfitting.

### What merging does

After training, `B·A` is just a fixed `out × in` matrix. `merge()` adds it into
the base weight once:

```python
W ← W + (α / r) · B · A        # computed in fp32, then cast to W's dtype
```

From then on, forward is a single matmul with the same cost as the base model, so
merged inference has zero LoRA overhead. That is claim L1 for P5a. The `merged`
flag makes `forward` skip the low-rank path, so the update is not applied twice.
`unmerge()` subtracts it again. `merge_lora(model)` merges every adapter and swaps
each wrapper back to a plain `nn.Linear`, so any loader or engine can use the
result.

The catch: on a bf16 base, merge-then-unmerge does not restore the weights
exactly (see [the bf16 issue](../issues/p0-bf16-unmerge-drift.md)).

### Why it saves memory

AdamW keeps two extra numbers (m and v) for every parameter it trains, and mixed
precision adds an fp32 master copy. Full fine-tuning therefore pays 16 bytes per
parameter, and 1.24B parameters × 16 B = 18.4 GiB. LoRA freezes the base, so the
base costs only its own 2 bytes per parameter. The 16-byte cost applies only to
the 11M adapter parameters (at r=16, all-linear). The details are in the results
section below.

## Design decisions

- **Mirror PEFT's layout.** The submodules are named `base_layer`, `lora_A`, and
  `lora_B`, and the scale is applied after B, as PEFT does. This has two benefits.
  First, our state-dict keys become PEFT's on-disk keys by adding a fixed prefix
  (`base_model.model.`), so saving and loading need no lookup table. Second, the
  floating-point operations run in the same order, so the logits match PEFT
  *bit-for-bit* in fp32 (measured max difference 0.0), not merely within 1e-5.
- **fp32 adapters on a bf16 base by default.** `inject_lora(adapter_dtype=fp32)`.
  bf16 can only represent changes of about 0.4% of a value. AdamW moves each
  weight by roughly the learning rate per step (2e-4, decaying toward zero under
  the cosine schedule). For a weight of size 0.02 that is already near bf16's
  resolution, and late in training many steps would round to no change at all.
  The adapter is tiny (11M parameters), so keeping it in fp32 costs little. Inside
  `forward`, the input is cast to the adapter dtype, and the sum is cast back to
  the base output dtype. Callers see bf16 in and bf16 out.
- **Target matching uses PEFT's suffix rule.** A target matches a module path if
  the path equals it or ends with `"." + target`. `"all-linear"` expands to the
  seven projections and never includes `lm_head`. In Llama 3.2 1B, `lm_head` is
  tied to the input embedding, so adapting it would also change the embedding.
- **Loading trusts the tensors, not `target_modules`.** PEFT writes
  `"all-linear"` to disk as a list of full module paths. Other tools write short
  names. `load_adapter` therefore wraps exactly the modules named in the
  safetensors file. It then checks that the config also selects each of them.
- **Refuse unsupported PEFT features loudly.** These are rsLoRA, DoRA, per-module
  rank or alpha patterns, `bias != "none"`, and `modules_to_save`. Loading an
  rsLoRA adapter (scale α/√r) with our α/r scale would produce plausible but wrong
  outputs. `from_peft_dict` raises `NotImplementedError` instead.
- **Analytic memory model, verified twice.** First, the counts are checked
  against a real model injected on the meta device. Second, the predicted steady
  state is checked against a measured MPS step (2.43 GiB predicted vs 2.431 GiB
  measured).

|---|---|---|---|---|---|
| full | — | — | 1,235,814,400 | 100 | 18.42 GiB |
| LoRA | q,v | 16 | 1,703,936 | 0.14 | 2.33 GiB |
| LoRA | q,k,v,o | 16 | 3,407,872 | 0.28 | 2.35 GiB |

**Measured on MPS** (LoRA r=16 all-linear, batch 1 × 256 tokens): the steady
state is 2.43 GiB, which matches the analytic prediction. The peak of live tensors
is 4.09 GiB, and a step takes 0.65 s. Full fine-tuning was not measured, because
its training state alone (18.4 GiB) exceeds the machine's 16 GiB.

## What was learned (gotchas)

1. **A new module starts in train mode.** Injecting adapters into a model that is
   already in `.eval()` mode silently turned dropout on. A test caught it, and
   `inject_lora` now copies the base layer's mode.
   ([issue](../issues/p0-injected-layers-start-in-train-mode.md))
2. **bf16 merge/unmerge is lossy.** Two roundings do not cancel. About 9% of the
   weights moved by one bf16 step after a round trip. Serving code should not
   switch adapters by repeated merge/unmerge on a bf16 base.
   ([issue](../issues/p0-bf16-unmerge-drift.md))
3. **Scripts in a worktree imported the main checkout.** The venv's editable
   install pointed at the main checkout. Scripts now put their own repository root
   first on `sys.path`.
   ([issue](../issues/p0-worktree-script-imports-main-checkout.md))
4. **Gradient tests are vacuous at init.** With B = 0, A's gradient is zero, so
   "our gradient equals PEFT's" holds trivially. The oracle tests randomize B
   first, and they also assert that the adapter changes the logits.
5. **PEFT rewrites `"all-linear"` on save** to a list of full module paths. A
   loader that only understood short names would fail on PEFT-trained adapters.
6. **After LoRA, activations become the memory bill.** For one 256-token
   sequence, the saved activations (1.3–1.7 GiB) are about ten times the
   adapter's whole training state (0.17 GiB). Dropout alone adds 0.37 GiB,
   because every adapter stores a mask over its own copy of the input.
7. **MPS has no `max_memory_allocated()`.** The best available peak is to sample
   `current_allocated_memory()` after each phase and to read
   `driver_allocated_memory()`. The driver number includes the allocator's cache,
   which only grows, so it works as a high-water mark.
8. **`PLAYPARSE_WEIGHTS` must be set in a worktree.** The default path resolves
   relative to the checkout, and from `.claude/worktrees/<name>` it points at a
   directory that does not exist.

## Open items

- The MPS measurement uses random tokens. Real PlayParse sequences (about 150
  tokens) will need less activation memory. Re-measure in P2 with real batches and
  with gradient checkpointing on and off.
- Loading in vLLM has not been tested here (no CUDA). The format matches PEFT's
  exactly, and vLLM reads PEFT's format, but the first P5b run should confirm it.
- `io.load_adapter` loads adapters only for modules that exist as `nn.Linear`. A
  QLoRA (P4) base uses bitsandbytes `Linear4bit`, so `LoRALinear` will need a
  4-bit base path then.
