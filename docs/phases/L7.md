# L7 — our multi-LoRA serving vs vLLM (pre-registered)

Written and committed **before** the L7 run.

## Why the metric is fixed here

The PRD's L7 threshold is "our goodput within 2× of vLLM's". The P5b H100 run showed
that the shared goodput SLO is degenerate: it was anchored on *unloaded* per-token
latency, which no batched system meets, so goodput is ≈ 0 in every cell
([`docs/benchmarks/p5b-cuda.md`](../benchmarks/p5b-cuda.md)). Comparing two near-zero
numbers says nothing. So L7 is judged on a load-insensitive measure, chosen now,
before either system runs.

## Design

- **Same allocation, same GPU** (one H100 job, `scripts/slurm/p5b_vllm.sbatch`): our
  serving layer (v2 kernel, 32 adapter slots, r=16, max batch 32) first, then vLLM
  (`--enable-lora`, `max_loras=32`, fp16) on the identical requests, adapters (exported
  in PEFT format from ours), and arrival times.
- **Cells:** N = 1, 4, 16, 64, 256 distinct adapters; uniform and Zipf popularity.
- **Metric:** saturation throughput — every cell's 512 requests replayed at t = 0,
  output tokens per second.
- **Threshold (unchanged factor):** **L7 earned if our saturation throughput is at
  least half of vLLM's in every cell.** Goodput and TTFT/TPOT at the offered rate are
  reported for both systems for information.
- **Also recorded:** whether vLLM loads our PEFT-format adapters without conversion.

## Result (job 13931464, H100, 2026-10-10) — L7 not earned

| N adapters | popularity | ours (v2) sat. tok/s | vLLM 0.31 sat. tok/s | ours / vLLM | ours TPOT p50 | vLLM TPOT p50 |
|---|---|---|---|---|---|---|
| 1 | — | 311 | 3,408 | 0.09 | 58.7 ms | 2.3 ms |
| 4 | uniform / zipf | 310 / 311 | 3,465 / 3,451 | 0.09 | ~60 ms | 2.2 ms |
| 16 | uniform / zipf | 309 / 308 | 3,197 / 3,248 | 0.10 | ~60 ms | 2.3 ms |
| 64 | uniform / zipf | 304 / 305 | 2,702 / 2,856 | 0.11 | ~63 ms | 2.4 ms |
| 256 | uniform / zipf | 300 / 305 | 2,378 / 2,735 | 0.13 / 0.11 | ~64 ms | 3.4 / 2.3 ms |

The threshold was ours ≥ 0.5 × vLLM in every cell; ours is 0.09–0.13×. **L7 is not
earned.** vLLM also met the goodput SLO for 98.8% of requests at N = 1 (39% at N = 256
uniform, where it starts swapping adapters), while ours met it for < 1% everywhere.

**Adapter compatibility:** vLLM loaded the PEFT-format adapters our code exports, with no
conversion, in every cell.

**Why ours is ~11× slower in throughput and ~25× in per-token latency.** The from-scratch
serving layer's paged attention loops over sequences in Python, it has no CUDA graphs
(every decode step pays thousands of kernel launches; P5a already showed launch overhead
dominating), and its LoRA path is two unfused matmuls per projection. vLLM uses fused
paged-attention kernels, CUDA graphs, and Punica-style fused multi-LoRA kernels.

**What does hold up:** relative scaling. From 1 to 256 adapters, ours keeps 96–98% of its
throughput; vLLM keeps 70–80% (its per-token latency rises at N = 256 uniform as it
swaps adapters through 32 GPU slots). Same pool size, same requests. That is a statement
about the adapter-pool design, not about absolute speed, and it is reported as such.

## Correction to an earlier statement

`docs/benchmarks/p5b-cuda.md` called the goodput SLO "degenerate" because no batched LoRA
arm of ours met it, and inferred that no batched system could. **That inference was
wrong**: vLLM meets the same SLO for 98.8% of requests. The SLO is fine; our serving layer
is too slow under batching (≈60 ms per token vs a 37 ms target). The L4 entry has been
corrected accordingly.
