# P3: integration and the first LoRA training pilot

P3's goal (PRD §11) is R5 (LoRA on ground truth), the hyperparameter sweep, the
data-size curve, and R7 (full fine-tune), resolving claims T1–T3 and T5. All of
that needs the H100, which is blocked on PACE access (BLOCKERS B3).

This document covers what P3 could do without the GPU:

1. **Integration.** Connecting the hand-written LoRA (P0), the eval harness (P1),
   and the training loop (P2) so that one trained adapter flows through training,
   in-training validation, the eval harness, and serving without conversion.
2. **A local pilot.** A real but reduced-scale training run on the M4 laptop,
   scored with the harness against R0 (regex) and R1 (zero-shot base model).
3. **The GPU plan.** Ready-to-run configs and Slurm commands for the full sweep.

The pilot's numbers are in [`docs/benchmarks/p3-local-pilot.md`](../benchmarks/p3-local-pilot.md).

## 1. Integration

### 1.1 One prompt for training and eval

An adapter is only meaningful on the exact prompt it was trained on. Training
builds prompts with `playparse.train.collate.encode_prompt`; the eval harness
renders them with `playparse.eval.baselines.hf_predictor.render_record` and
tokenizes a left-padded batch. Two things could make them drift apart: the
chat-template date (the Llama template writes today's date into the system
header unless it is pinned), and tokenization details (a duplicated BOS token,
padding).

The pinned date existed twice, once per phase. There is now a single
`CHAT_DATE_STRING` in `playparse/prompt.py`, imported by both sides.
`tests/test_prompt_parity.py` checks that both paths produce byte-identical token
ids for every fixture record, including after the harness's batch padding is
removed. Issue: [`p3-duplicated-chat-date`](../issues/p3-duplicated-chat-date.md).

### 1.2 Own LoRA by default, saved in PEFT format

`lora.impl` now defaults to `playparse` (the P0 implementation). Checkpoints,
`best/`, and the final adapter are written by `playparse.lora.io.save_adapter`
in PEFT's on-disk format: `adapter_config.json` plus `adapter_model.safetensors`
with PEFT key names. On resume, the load function checks the saved rank and
alpha against the run before filling the layers.

Why it matters: the adapter a run produces can be loaded unchanged by serving
(`playparse.serving.adapter.load_peft_adapter`, P5a/P5b), by
`PeftModel.from_pretrained`, and by vLLM. `tests/test_p3_adapter_io.py` trains a
tiny run and checks all three loaders, logit equality with PEFT, and exact
resume. Issue: [`p3-lora-checkpoints-not-peft-format`](../issues/p3-lora-checkpoints-not-peft-format.md).

### 1.3 The eval metrics as the training val callback

`playparse/train/val_eval.py` replaces P2's placeholder callback. Every
`gen_every` steps it greedy-decodes a fixed val subset with
`playparse.train.generate` and scores each output with
`playparse.eval.metrics.score_example`, the harness's own parser.

The subset is **seeded and stratified by bucket**. That matters because val is
84% normal plays and has only 16 laterals in 38,102 plays; the old callback took
the first N plays of the file, which are a few games of mostly normal plays.
Because a balanced subset does not have the natural bucket mix, three overall
numbers are logged:

| Key | Meaning |
|---|---|
| `val_exact_match` | Average over the subset as drawn |
| `val_exact_match_natural` | Per-bucket exact match reweighted to the full val file's bucket shares |
| `val_exact_match_macro` | Plain mean over buckets |

Per-bucket keys (`val_exact_match/<bucket>`, `val_n/<bucket>`), valid rate, and
credit F1 are logged too. Any of them can be the `early_stop_metric`, and
`save_best` keeps the best adapter. Val loss can likewise use a stratified sample
(`data.val_loss_examples`). Issue: [`p3-val-callback-head-of-file`](../issues/p3-val-callback-head-of-file.md).

### 1.4 A LoRA rung in the eval CLI

```bash
python -m playparse.eval.run --rung lora --adapter runs/r5/best \
    --data data/processed/eval_lite.jsonl --out results/r5_eval_lite [--merge] [--dtype bfloat16]
```

`LoRAPredictor` subclasses the R1 predictor and only adds the adapter after the
base model loads. So prompt rendering, tokenization, padding, greedy decoding,
and stop handling are exactly R1's: the only difference between R1 and the LoRA
rung is the adapter. `--merge` folds the adapter into the base weights first. The
adapter's weight hash, rank, alpha, targets, and the merge flag go into the
config hash. `--dtype` is new for all HF rungs, so R1 and the adapter can be
compared at the precision the adapter was trained in.

`tests/test_lora_rung.py` (tiny Llama with the real tokenizer) checks that the
adapter changes outputs, merged equals unmerged, the harness's decoding matches
`playparse.train.generate` token for token (so in-training and post-training
scores are comparable), and the CLI writes the adapter fingerprint.

### 1.5 Smaller fixes found on the way

- **max_len.** Six train plays (four laterals, two challenges) exceed the old
  default `max_len: 512`; the longest is 595 tokens. With
  `on_overlength: raise`, the first full run would have stopped at startup. The
  default is now 640. Issue: [`p3-default-max-len-too-short`](../issues/p3-default-max-len-too-short.md).
- **Nested data-size samples.** The data-size curve needs random subsets where
  the 1k sample sits inside the 5k sample. `data.train_sample` takes the first N
  of a seeded permutation (the old `limit_train` takes the head of a
  game-ordered file).

### 1.6 Tests

All default tests run on CPU in about 20 seconds (537 passed at the last
commit, up from 512 before P3). New files:

| File | Covers |
|---|---|
| `tests/test_prompt_parity.py` | One date constant; training and harness prompt ids identical, also after batch padding |
| `tests/test_p3_adapter_io.py` | Default impl; PEFT-format checkpoints; loading in playparse, PEFT, and serving; rank mismatch; exact resume |
| `tests/test_val_eval.py` | Stratified subsets; scoring; per-bucket early stopping and best adapter inside `train()` |
| `tests/test_lora_rung.py` | Adapter changes outputs; merged = unmerged; harness = `train.generate`; CLI end to end |
| `tests/test_p3_pilot.py` | Pilot data selection (water-filled allocation); paired bootstrap differences |
| `tests/test_p3_sweep.py` | Every sweep command resolves to a valid RunSpec; matched-budget ranks; nested samples |
| `tests/test_p3_dataset_lengths_slow.py` | `slow`: every train/val example fits the default `max_len` |

Relevant slow tests were run on the real model after the pilot (see the final
section of this document).

## 2. The local pilot

Full write-up: [`docs/benchmarks/p3-local-pilot.md`](../benchmarks/p3-local-pilot.md).
Artifacts: `results/p3_local_pilot/`.

### Design

Full-scale training needs the H100: one epoch over train is 87.9 million tokens,
about 105 hours at the laptop's 233 tokens/s. The pilot was sized to fit in
roughly two hours of training:

- **2,400 training plays**, deliberately enriched: all 166 train laterals, about
  148 of each other non-normal bucket, and 1,200 normal plays. Half the data is
  "hard" versus 16% in train. This makes the pilot say something about the
  buckets that matter for T3, at the price of a training distribution that is
  not the natural one.
- **The PRD defaults** at laptop batch size: r=16, alpha=32, all-linear, dropout
  0.05, lr 2e-4, micro-batch 1 × accumulation 8, one epoch (300 steps).
- **Eval**: all 814 non-normal plays of `eval_lite.jsonl` plus 200 seeded normal
  plays, scored by the harness for the adapter, R0, and R1 (same batch size and
  dtype), and R2 on a 108-play balanced slice.

### Results

| bucket | n | pilot adapter | R0 regex | R1 zero-shot |
|---|---|---|---|---|
| overall | 1014 | 93.7 [91.7, 95.3] | 97.6 [96.5, 98.5] | 0.0 |
| penalty_stands | 100 | 80.0 [73.0, 87.8] | 100.0 | 0.0 |
| fumble | 100 | 76.0 [68.4, 83.7] | 92.0 [86.3, 97.1] | 0.0 |
| lateral | 29 | 48.3 [30.0, 66.7] | 62.1 [42.9, 79.2] | 0.0 |
| challenge | 100 | 96.0 [92.1, 100.0] | 96.0 [91.8, 99.1] | 0.0 |
| other 5 buckets | 685 | 99.9 | 99.9 | 0.0 |

R2 on its 108-play slice: 16.7% (adapter 98/108, R0 102/108).

### What it shows

- **Fine-tuning is what makes the 1B model usable.** Zero-shot, the model almost
  never emits the schema (24.7% valid, 0% exact). Few-shot gets format right
  70% of the time but content right 17%. 300 steps of LoRA reach 93.7% exact
  and 100% schema-exact output.
- **The small adapter loses to the regex on three hard buckets** (paired
  differences exclude zero): penalty_stands −20 points, fumble −16, lateral −14.
  It is right where R0 is wrong on only 2 of 1,014 plays.
- **The failures are arithmetic the labels require but the text does not state.**
  On val plays from those buckets (the test-season text was not read), the
  adapter gets players and stat types right but yardage wrong: accepted
  holding penalties enforced at a spot need the yards up to the spot, and
  fumble plays use official yards that differ from the stated gain. R0 encodes
  these rules explicitly.
- **The adapter was still improving** at the end (balanced val exact match
  78% → 86% → 91% at steps 100/200/300; best checkpoint = last).

### Limits

About 1% of the data, one epoch, an enriched training mix, a shared laptop with
other agents' jobs (throughput varied 20×; see
[`p3-shared-mps-contention`](../issues/p3-shared-mps-contention.md)), and an
eval set that is 80% hard plays. None of the T1–T3 claims is resolved by this.

### What it means for the GPU runs

1. **T3 hinges on yard arithmetic.** Watch `val_exact_match/penalty_stands` and
   `/fumble` during R5, not just the overall number. If the full-data adapter
   still misses spot fouls, candidate fixes are (a) more spot-foul examples, (b)
   a short rule in the system prompt, or (c) accepting that a hybrid
   (regex for yardage, model for structure) is the right answer, which is itself
   a ladder finding worth publishing.
2. **Prompt tokens are 89% of compute.** A prompt-length ablation (short or no
   system prompt once the adapter has learned the format) is the cheapest
   large speedup available for both training and serving.
3. **Enrichment is a knob.** The natural distribution gives ~120 laterals per
   epoch at 50k plays; a hard-bucket enrichment ratio belongs in the sweep as an
   extra knob after the PRD ones.

## 3. The GPU plan (waiting on B3)

### Status

Everything is ready except cluster access (B3). Fill in the `>>> FILL IN <<<`
lines in `scripts/slurm/train_h100.sbatch` (account, QOS, paths, GPU gres), then:

```bash
# Preview every command (25 runs), then submit one group at a time.
bash scripts/slurm/p3_sweep.sh all
SUBMIT=1 bash scripts/slurm/p3_sweep.sh r5        # R5: default config, full train, 2 epochs
SUBMIT=1 bash scripts/slurm/p3_sweep.sh rank      # r in 2 4 8 16 64, alpha = 2r
SUBMIT=1 bash scripts/slurm/p3_sweep.sh alpha     # alpha = r at r=16; alpha fixed at 16 for r in 2 4 8 64
SUBMIT=1 bash scripts/slurm/p3_sweep.sh targets   # {q,v}, {q,k,v,o} at r=16 and at a matched budget (r=106, r=53)
SUBMIT=1 bash scripts/slurm/p3_sweep.sh dropout   # 0, 0.1 (0.05 = base)
SUBMIT=1 bash scripts/slurm/p3_sweep.sh lr        # 5e-5 1e-4 5e-4 1e-3 (2e-4 = base)
SUBMIT=1 bash scripts/slurm/p3_sweep.sh datasize  # 1k 5k 20k 100k nested samples of full train (full = R5)
```

Each job resumes automatically from its newest checkpoint if resubmitted, and
requeues itself five minutes before the time limit.

| Config | What it is |
|---|---|
| `configs/train_default.yaml` | R5 and the data-size curve: full train, PRD §8.4 defaults, micro 16 × accum 4, 2 epochs, early stop on balanced val exact match (patience 4), `max_len` 640, val loss on 2,000 stratified val plays, generation eval on 500 balanced val plays |
| `configs/p3_sweep_50k.yaml` | Same defaults on `train_50k.jsonl`, with eval/gen/save every 100/200/200 steps; one knob is overridden per sweep run |

### After training

Score each run's best adapter with the same harness as R0–R4, on eval_lite for
the sweep and on the frozen test set once, for the chosen R5 only:

```bash
python -m playparse.eval.run --rung lora --adapter runs/sweep/<run>/best \
    --data data/processed/eval_lite.jsonl --out results/p3_sweep/<run> --batch-size 32
python -m playparse.eval.run --rung lora --adapter runs/sweep/r5_full/best \
    --data data/processed/test.jsonl --out results/r5_test --batch-size 32
```

R1–R3 on eval_lite should run on the H100 too (locally R1 is 0.3 plays/s and R2
0.1 plays/s), so that every ladder row comes from the same hardware.

### Rough cost (to be replaced by the first job's measurement)

Per epoch, full train is 87.9 M real tokens (100 M padded to 64); the 50k subset
is about 15 M. Assuming 15,000–30,000 tokens/s for LoRA on a 1B model on one
H100 (an assumption, not a measurement), R5's two epochs take about 2–3.5 hours
and each 50k sweep run about 20–35 minutes plus generation evals, so the 20
sweep runs need roughly 8–14 GPU hours. The first R5 job's `tokens_per_sec` in
`metrics.jsonl` replaces this estimate.

## 4. Slow tests on the real model

Run after the pilot, with no other job on the machine:

```bash
python -m pytest -q -m slow tests/test_lora_slow.py tests/test_p2_smoke_slow.py \
    tests/test_hf_predictor.py tests/test_p3_dataset_lengths_slow.py
# 5 passed in 202 s
```

They cover: the hand-written LoRA's logits on the real 1B model against PEFT,
the P2 real-model smoke run (loss decreases), the R1 smoke run through the
harness, and the full-dataset `max_len` check on train and val. The pilot itself
is the end-to-end real-model test of the new integration: the default
`playparse` LoRA trained on MPS, its PEFT-format checkpoint loaded into the LoRA
rung, and the merged and unmerged paths agreed on 63 of 64 plays (bf16 merge
rounding explains the one difference).

## Issues found in P3

- [`p3-duplicated-chat-date`](../issues/p3-duplicated-chat-date.md): the pinned template date was defined in two places.
- [`p3-lora-checkpoints-not-peft-format`](../issues/p3-lora-checkpoints-not-peft-format.md): training with the own LoRA wrote checkpoints no downstream loader could read.
- [`p3-val-callback-head-of-file`](../issues/p3-val-callback-head-of-file.md): in-training validation scored the first N val plays, almost all normal.
- [`p3-default-max-len-too-short`](../issues/p3-default-max-len-too-short.md): six train plays exceed 512 tokens; the first full run would have crashed.
- [`p3-pilot-allocation-ignored-caps`](../issues/p3-pilot-allocation-ignored-caps.md): the pilot's bucket allocation mishandled small buckets (no effect on the real run).
- [`p3-shared-mps-contention`](../issues/p3-shared-mps-contention.md): another agent's real-model jobs overlapped the pilot and slowed it up to 20×.
