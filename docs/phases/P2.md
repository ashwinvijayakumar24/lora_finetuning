# P2: the hand-written training loop

P2 builds the supervised fine-tuning (SFT) loop by hand in plain PyTorch: how
examples become batches, how the loss is computed, how gradients from several
small batches are combined, how a run is saved and resumed, and how a trained
model generates text. No Hugging Face `Trainer` or TRL is used in the
implementation. They appear only as references in tests.

This document explains each mechanism, why it is built the way it is, and which
test proves it works. Smoke-run measurements on the real 1B model are at the end.

## Files

| File | What it does |
|---|---|
| `playparse/train/collate.py` | Records → token ids and labels → padded batches |
| `playparse/train/loop.py` | `train()`: optimizer, schedule, accumulation, eval, checkpoints |
| `playparse/train/generate.py` | Batched greedy decoding for eval |
| `playparse/train/build.py` | Load base model, add LoRA, run spec (config file) |
| `playparse/train/synthetic.py` | Template plays for smoke tests |

| `scripts/p2_smoke_train.py` | Real-model smoke run and benchmark |
| `scripts/slurm/train_h100.sbatch` | Slurm job template for one H100 on PACE Phoenix |
| `configs/train_default.yaml` | Default run spec (PRD §8.4 values) |

## 1. What one training example looks like

An example is a prompt followed by a completion:

```
prompt     = chat template applied to build_messages(posteam, desc),
             ending with the assistant header
completion = PlayLabel.to_json() + <|eot_id|>
```

Concretely, for a 14-yard completion the token sequence is (abridged):

```
<|begin_of_text|><|start_header_id|>system<|end_header_id|>\n\n
Cutting Knowledge Date: December 2023\nToday Date: 26 Jul 2024\n\n
You extract fantasy-football stat credits ... <|eot_id|>
<|start_header_id|>user<|end_header_id|>\n\nposteam: PHI\ndesc: ... <|eot_id|>
<|start_header_id|>assistant<|end_header_id|>\n\n          ← prompt ends here
{"nullified":false,"credits":[...]}<|eot_id|>                ← completion
```

A typical example is about 260 tokens. Only about 30 to 60 of them are the
completion. The system prompt alone is about 200 tokens.

### Which token ends the answer

Llama 3.2 Instruct has three "end" tokens, and picking the wrong one is a common
mistake:

| Token | Id | Meaning |
|---|---|---|
| `<|eot_id|>` | 128009 | End of one chat turn. The chat template closes every turn with it. |
| `<|end_of_text|>` | 128001 | End of a whole document in pre-training. Never appears inside a chat. |
| `<|eom_id|>` | 128008 | End of a message that hands off to a tool. |

The completion must end in `<|eot_id|>`, because that is what the template puts
after an assistant turn and what the model learned to emit at the end of an
answer. It is also `tokenizer.eos_token` for this checkpoint.
`end_of_turn_id(tokenizer)` returns it. Generation stops on any of the three
(`stop_token_ids`), with `<|eot_id|>` first.

**Test:** `test_end_of_turn_is_eot_not_end_of_text` checks the template really
closes the assistant turn with `<|eot_id|>`.

## 2. Why mask the prompt

The model is trained with next-token prediction: at every position it predicts the
next token, and the loss is the cross-entropy of that prediction. If every token
counted, most of the loss would come from the prompt. The system prompt is the
same in every example, so the model would spend much of its learning on
memorizing a fixed paragraph. It would also learn to "predict" the play text,
which it will always be given and never needs to produce.

Completion-only loss fixes this. Prompt positions get the label `-100`, which
PyTorch's cross-entropy ignores (`ignore_index`). The gradient then comes only
from the part we want the model to get right: the JSON and the end-of-turn token.

The `mask_prompt=False` option turns this off on purpose. It exists for two later
uses: a masking ablation (does masking actually help eval scores on this task?)
and a deliberately weaker adapter for the registry's rejection demo in P6.

### The shift by one

Labels are stored aligned with `input_ids`: `labels[i]` is the token at position
`i`. The logits at position `i` predict token `i + 1`. So the loss compares
`logits[:, :-1]` with `labels[:, 1:]` (`token_loss_sum` in `loop.py`). A
consequence: the first completion token is predicted from the last prompt
position (the `\n\n` after the assistant header). That position's label is
`-100`, but what matters is the *next* label, which is the first completion
token. So every completion token, including the first, is scored.

**Tests:**
- `test_mask_covers_exactly_the_completion`: the supervised tokens decode to
  exactly the label JSON plus `<|eot_id|>`.
- `test_collate_right_pads_and_masks_padding`: after the shift, the number of
  scored positions equals the number of completion tokens.
- `test_mask_prompt_false_changes_the_loss` and
  `test_mask_prompt_false_supervises_everything`.

## 3. Tokenization traps

### The duplicated BOS

The Llama chat template begins with `<|begin_of_text|>` (BOS, the
beginning-of-sequence token). A tokenizer called with its default
`add_special_tokens=True` also adds a BOS. Render the template to a string, then
tokenize that string the usual way, and the sequence starts with two BOS tokens:

```python
text = tokenizer.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True)
tokenizer(text)["input_ids"][:3]                          # [128000, 128000, 128006]  wrong
tokenizer(text, add_special_tokens=False)["input_ids"][:3] # [128000, 128006, 9125]   right
```

Nothing crashes. The model just trains on a sequence shape it never saw in
pre-training, and serving code that tokenizes correctly then sends a different
sequence than training did. `encode_prompt` tokenizes with
`add_special_tokens=False` and asserts that there is exactly one BOS, at
position 0.

**Test:** `test_bos_not_duplicated` demonstrates the trap and checks our encoding.

### The date in the prompt

The template writes `Today Date: <today>` into the system header. Left alone,
the prompt changes every day. We pin `date_string=DEFAULT_DATE_STRING`
(`"26 Jul 2024"`, a module constant in `collate.py`). See
[`docs/issues/p2-chat-template-date.md`](../issues/p2-chat-template-date.md).

**Tests:** `test_prompt_is_date_independent`, and
`test_rendering_is_stable_regardless_of_system_date`, which fakes the clock the
template reads and shows the unpinned prompt changes while ours does not.

### Tokenizing prompt and completion separately

We tokenize the prompt and the completion separately and join the id lists. This
matches inference exactly: at serving time the model receives the prompt ids and
generates the completion one id at a time, so no BPE merge (the tokenizer joining
characters into one token) can cross the boundary. A test confirms that, for this
template, the joined ids also equal tokenizing the whole conversation at once.
The `\n\n` before the JSON does not merge with `{`.

**Test:** `test_full_sequence_matches_template_with_assistant_turn`.

### No silent truncation

If an example is longer than `max_len`, `encode_record` raises
`OverLengthError`. Truncating would cut off the end of the sequence, which is
exactly the completion and its `<|eot_id|>`. The model would then learn to stop
mid-JSON. `encode_records(..., on_overlength="drop")` skips such examples but
lists every one in the returned report, so dropping is never silent.

**Test:** `test_over_length_raises_and_drop_reports`.

### Padding side

Training pads on the right. With a causal mask (each token sees only earlier
tokens), real tokens never look at pads that come after them, so outputs are
unchanged. Generation pads on the left, explained in section 7.

**Test:** `test_padding_does_not_change_the_loss`: an example's loss is the same
alone or in a padded batch.

## 4. Gradient accumulation and why normalization matters

A large effective batch (64 examples in the default config) may not fit in memory
at once. Gradient accumulation runs several small *micro-batches*, adds up their
gradients, and takes one optimizer step. The question is what to divide by.

### The correct rule

The loss we want is the mean over all completion tokens in the whole effective
batch:

```
L = (sum of token losses over all G micro-batches) / N
N = total completion tokens across all G micro-batches
```

Because a sum splits cleanly, each micro-batch can contribute
`(its summed token loss) / N` and the gradients add up to exactly `∇L`. The loop
counts `N` from the labels *before* any forward pass (labels are known up front),
then calls `backward(loss_sum / N)` per micro-batch.

### The bug

The tempting version computes each micro-batch's *mean* loss, as a normal
training step would, and divides by `G`:

```
L_naive = (1/G) · Σ_g (sum of token losses in g) / n_g
```

This equals `L` only when every micro-batch has the same number of completion
tokens. Our completions vary a lot in length: a nullified play is about 12
tokens, and a touchdown pass with five credits is about 70.

### Worked example

Two micro-batches, accumulated into one step:

- Micro-batch A: 1 example, a nullified play, 10 completion tokens, each with
  loss 2.0. Summed loss 20.
- Micro-batch B: 1 example, a touchdown pass, 90 completion tokens, each with
  loss 1.0. Summed loss 90.

Correct: `L = (20 + 90) / (10 + 90) = 1.10`. Each of the 100 tokens has weight
1/100.

Naive: `L_naive = ½ · (20/10 + 90/90) = ½ · (2.0 + 1.0) = 1.50`. Each token in A
now has weight 1/20, and each token in B has weight 1/180. A token in the short
example counts **9 times** as much as a token in the long one.

The effect on training: short completions (nullified plays, incompletions) get
over-weighted, and long multi-credit plays, the hard cases, get under-weighted.
The result also changes with micro-batch size, so a run on a 16 GB laptop
(micro-batch 1) and a run on an H100 (micro-batch 16) with the same effective
batch would optimize different objectives.

**Tests:**
- `test_grad_accum_matches_one_big_batch`: 4 micro-batches × accumulation 4 gives
  the same gradient as one batch of 16 with variable-length completions (relative
  difference below 1e-5).
- `test_naive_per_micro_batch_mean_is_wrong`: the naive rule on the same data is
  off by more than 1%, which is orders of magnitude above floating-point noise.
  This is the test that would catch the bug.
- `test_loop_step_with_accum_equals_big_batch_step`: through the full `train()`
  loop, one optimizer step with micro 4 × accum 4 lands on the same weights as
  micro 16.

On a multi-GPU setup, `N` would also need summing across GPUs. The loop is
single-device for now.

## 5. The rest of an optimizer step

- **AdamW over trainable parameters only.** The optimizer receives only
  parameters with `requires_grad=True`. With LoRA that is about 0.9% of the 1.24B
  parameters, so the Adam moment buffers are about 90 MB instead of about 10 GB.
  Test: `test_only_requires_grad_params_change` (every frozen weight is
  bit-identical after training; every adapter weight moved).
- **Schedule.** Linear warmup from `lr/warmup` to `lr`, then a half cosine down
  to `lr · min_lr_ratio`. Tests: `test_lr_schedule_warmup_then_cosine` and
  `test_lr_logged_follows_schedule`.
- **Gradient clipping** to `max_grad_norm` (1.0 by default). The pre-clip norm is
  logged, which is a useful signal of instability.
- **Precision.** On CUDA, the forward pass runs under bf16 autocast. On MPS and
  CPU the default is no autocast: the frozen base is loaded in bf16 and the LoRA
  weights stay in fp32 (PEFT keeps adapters in fp32). The loss itself is always
  computed in fp32. Only the scored positions are upcast, so the fp32 copy is
  (completion tokens × vocabulary) rather than (all tokens × vocabulary).

## 6. What a checkpoint must contain to resume exactly

"Resume" should mean the run continues as if it had never stopped: the same
losses, the same final weights. That requires saving every piece of state that
influences the future, not just the weights:

| Saved | Why it is needed |
|---|---|
| Adapter weights | The thing being trained. Adapter-only: the frozen base is reloaded from the original weights, so a checkpoint is MBs, not GBs. |
| Optimizer state | AdamW keeps two running averages per parameter. Without them the first steps after resume behave like a cold start. |
| Scheduler state | Where we are on the warmup/cosine curve. |
| Step counter | Which examples come next, and when to evaluate and save. |
| RNG states (Python, NumPy, torch CPU, CUDA, MPS) | LoRA dropout draws random masks. Different random numbers after resume mean a different run. |
| Early-stopping state | The best score so far and how many evaluations have passed without improvement. |

What is deliberately **not** saved is the data loader. The example order is a
pure function of `(seed, step)`: epoch `e` is a permutation seeded with
`seed + e`, and step `s` takes positions `[s·k, (s+1)·k)` of the endless
concatenation of epochs. Resuming at step `s` reproduces the order with no
sampler state to save (`DataOrder`).

Checkpoints are written to a temporary directory and renamed into place, so a
job killed mid-save never leaves a half-written checkpoint that looks complete.
Only the newest `keep_last_checkpoints` are kept.

Adapter saving and loading are injectable callables. The default saves every
`requires_grad` parameter to `trainable.safetensors`. `build.apply_lora` passes
PEFT's `save_pretrained` format when PEFT is used, and the hand-written
`playparse.lora` can supply its own PEFT-format writer.

**Tests:**
- `test_resume_reproduces_uninterrupted_run[safetensors|peft]`: train 8 steps in
  one go; separately, train 4 steps, stop, then resume in a "fresh process" whose
  adapter weights and RNG were deliberately scrambled. The final weights are
  bit-identical (`torch.equal`), and every step's loss and the final val loss
  match exactly. Dropout is on and the run crosses an epoch boundary, so RNG and
  data order both matter.
- `test_checkpoint_contents`: the checkpoint holds every field above, and the
  adapter file holds only trainable parameters.

Exact equality holds on CPU. On a GPU, some kernels are not bit-deterministic.
`deterministic: true` turns on `torch.use_deterministic_algorithms` for CUDA. Even
without it, a resumed run should match to within float noise.

## 7. Generation for eval

`generate.py` decodes greedily (always the most likely token), in batches.

Generation pads on the **left**. New tokens are appended on the right of every
row. With right padding, a short prompt's next token would land after its pads.
Left padding lines up every prompt's last real token in the final column, so one
`argmax` over the last position serves the whole batch. Position ids come from
the attention mask (`cumsum - 1`), so a left-padded prompt still sees positions
0 to n-1. The KV cache (the stored attention keys and values from earlier
positions) is reused, so each new token costs one position of compute, not a
full re-run.

Each row stops at its first stop token. The returned text excludes the stop token
but keeps any other special token, so malformed output stays visible to eval.

**Tests:** a tiny model is trained to memorize 8 completions, then:
- `test_trained_model_reproduces_completions_and_stops_on_eot`: generation
  reproduces every completion and stops on the end-of-turn id.
- `test_batching_is_invisible_and_matches_hf_generate`: batched output equals
  one-at-a-time output, and both equal Hugging Face `generate` token for token,
  including on unseen prompts.
- `test_stops_on_any_stop_token`.

## 8. Logging, evaluation hooks, early stopping

Every run writes `<output_dir>/metrics.jsonl`, one JSON object per line, tagged by
`event`:

- `train`: step, epoch, train loss (token-weighted over the logging window), lr,
  grad norm, target tokens, tokens/sec, step time, peak memory.
- `eval`: val loss (the same token-weighted quantity as the train loss).
- `val_callback`: whatever the callback returns, for example
  `val_exact_match` and `val_parse_rate`.
- `checkpoint`, `best`, `early_stop`, `resume`, `start`, `end`.

`val_callback(model, step)` runs every `gen_every` steps with the model in eval
mode. `build.exact_match_callback` is a placeholder that generates on N val
records and scores them with `PlayLabel.from_json` and `matches`. The P1 eval
harness can replace it.

Early stopping watches any logged metric (`early_stop_metric`, `min` or `max`)
and stops after `early_stop_patience` evaluations without improvement. A
`should_stop(step, metrics)` hook allows any other rule.

Peak memory is measured per backend: exact on CUDA, sampled on MPS (see the smoke
results), and process peak RSS (resident memory) on CPU.

## 9. Running it

Locally, or on any machine:

```bash
python scripts/train.py --config configs/train_default.yaml \
    --set data.train=data/processed/train.jsonl data.val=data/processed/val.jsonl \
          train.output_dir=runs/r5

# resume after a crash
python scripts/train.py --config runs/r5/run_spec.json --resume latest
```

On PACE Phoenix (after filling in the `>>> FILL IN <<<` lines):

```bash
sbatch scripts/slurm/train_h100.sbatch configs/train_default.yaml runs/r5
```

The Slurm job resumes automatically if the output directory already has
checkpoints. It asks Slurm for a warning signal 5 minutes before the time limit
and requeues itself, so long runs and preemptions continue from the last
checkpoint.

## 11. Smoke run on the real model (Apple M4, MPS)

Full write-up: [`docs/benchmarks/p2-smoke-mps.md`](../benchmarks/p2-smoke-mps.md).
Raw record: [`results/p2/smoke.json`](../../results/p2/smoke.json).

The loop trains the real model correctly on MPS, but local throughput rules out
real training runs on the laptop.

| | |
|---|---|
| Setup | Llama 3.2 1B (bf16) + PEFT LoRA r=16 all-linear, micro-batch 1 × accum 8, lr 2e-4, 30 steps, 64 template plays |
| Train loss | 0.459 → 0.005 |
| Val loss | 0.062 (step 7) → 0.011 (step 30) |
| Exact match, 16 held-out template plays | 0% → 94% (valid JSON 38% → 100%) |
| Throughput | 144 tokens/s (20 completion tokens/s), 14.6 s per step |
| Peak memory | 6.36 GiB Metal driver total, 5.35 GiB live tensors |
| Adapter checkpoint | 45 MB |

At 144 tokens/s, one epoch over 100,000 real examples (about 26 million tokens)
would take about 50 hours. The laptop is for tests, smoke runs, and debugging;
sweeps need the H100.

Getting this run to work surfaced two problems, both now fixed and documented:
micro-batch 4 needed about 13 GB, and a non-blocking copy to MPS corrupted
labels. Note also that the smoke run used the system prompt as it was on this
branch; main has since reworded the reversal rule, which changes prompt lengths
by a few tokens.

## Issues found in P2

- [`p2-chat-template-date`](../issues/p2-chat-template-date.md): the template puts today's date in the prompt.
- [`p2-apply-chat-template-returns-batchencoding`](../issues/p2-apply-chat-template-returns-batchencoding.md): `tokenize=True` returns a dict in transformers 5.
- [`p2-tiny-lora-loss-floor`](../issues/p2-tiny-lora-loss-floor.md): a toy model with LoRA cannot memorize, for reasons unrelated to the loop.
- [`p2-mps-activation-memory`](../issues/p2-mps-activation-memory.md): micro-batch 4 pushed the 16 GB laptop into swap; varying shapes fragmented the MPS cache.
- [`p2-mps-nonblocking-copy-race`](../issues/p2-mps-nonblocking-copy-race.md): `non_blocking=True` copies to MPS fed garbage labels to the loss. The most serious bug of the phase, because it was silent.
